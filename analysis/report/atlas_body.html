Summary

What the analysis found

  1. The ~2.6M comes entirely from greedy_density: on the four official instances. local_search never makes a move after it, on any instance.
  2. Against provable upper bounds the greedy is within 2% of optimal on every official instance. It is below the true optimum on me_at_the_zoo (solved exactly: ), at most on videos_worth_spreading, at most on kittens and at most on trending_today. No algorithm can add more than points to the 2.64M total.
  3. Three features decide which algorithm helps. Capacity pressure decides whether the problem is packing or selection. Item granularity decides whether knapsack integrality costs anything. Cache overlap decides whether the problem splits per cache or turns into a coverage problem.
  4. Ranking by density (gain ÷ size) is essential when capacity is scarce and sizes vary: switching to raw gain lost 81% on universalLambda and 54% on dejaVu. On trending_today, where everything fits, it is the wrong ranking.
  5. An exact per-cache knapsack re-optimisation (the "replace" move the current local search lacks) adds 0.2–0.8% wherever caches overlap little, and nothing on trending_today.
  6. Two correctness issues turned up: an uninitialised request counter in the parser, and 41 duplicated endpoint→cache links in the dejaVu instance that the greedy and the local search read differently.

Algorithm response

How each instance reacts to each algorithm

Four configurations of the team's own code (the solvers of parser.cpp, run by analysis/team_driver.cpp), each run once per instance. Base greedy: greedy_density, always placing the best (video, cache) pair by gain per MB. Greedy 90%: the same, but each placement takes the runner-up pair with probability 10%. + R&R: greedy 90%, then ruin & recreate until the time limit; each iteration empties a third of the caches, drawn at random (ruin probability 100%), refills them with greedy 90% and keeps the result only if it scores higher. + R&R + knapsack: as in parser.cpp's main, rounds of 30 ruin & recreate iterations, each round followed by knapsack_reopt, until the time limit.

Found along the way

Code and data issues

Bug

Uninitialised request counter in the parser

int video_id, endpoint_id, count, Rprime; in requestParser (parser.cpp:144) never sets Rprime = 0. On this machine it started near 32,766, so ip.R came out as 32,770 on the 5-request example. The requests array is then allocated with ~32k extra slots whose count is uninitialised, and computeContestScore adds those counts to its denominator. Scores are only right because fresh heap pages happen to be zero. Fix: int Rprime = 0;.

Bug

Duplicated endpoint→cache links in custom_dejavu42

The dejaVu generator draws each endpoint's 4 caches with replacement (rng.randint(0, C, size=CACHE_CONNECTIONS), instanceCreator.py:138), so 39 of 115 endpoints list the same cache twice with two different latencies (41 links in total). The validator does not check for this. latencyToCache in the greedy takes the first link, while compute_updated_score in the local search takes the best. So the same solution scores 64,148 in one and 64,654 in the other. Chaining them does real damage: run after the greedy, local_search removes video 9984 from cache 16 and reports an improvement from 64,148 to 64,646, but under a consistent reading the solution got worse, from 64,654 to 64,646. Fix: sample with rng.choice(C, 4, replace=False), or keep the lowest latency when parsing.

Method

The local search cannot move after the greedy

This is guaranteed, not a coincidence. The greedy stops only when no video with positive gain fits in any cache. Removing a video never helps. And if moving video v from cache a to cache b improved the score, adding v to b while keeping it in a would improve it at least as much, which the stopping rule already excludes. So local_search can never move after greedy_density, unless the two disagree on latencies as they do on dejaVu. The neighbourhood needs a replace move (take video a out of cache c and put video b in), which is what the per-cache knapsack re-optimisation applies optimally.

Minor

Smaller things

local_search returns the iteration index when it converges but the score when it runs out of iterations (local_search.cpp:180). The endpoint loop in showInstance increments with k<k++ (parser.cpp:247). The two example.in copies differ: the generator repo's copy has endpoint 0 at 200 ms instead of 1000 ms. The generator repo's instance files use CRLF line endings; std::cin handles them, but piping them through line-based tools needs tr -d '\r'.

How the bounds were computed. Uncapacitated: every request served from its best connected cache. Coverage: for each video, k copies are worth at most min(total demand value, sum of its k best single-cache gains); relaxing integrality and pooling all capacity gives a fractional knapsack. Aggregated LP: the same idea with per-cache capacity kept. Full LP: the facility-location relaxation (yrc ≤ xvc, Σc yrc ≤ 1, per-cache capacity). MIP: the full model with integer placements, solved to proven optimality with HiGHS. Each row reports the tightest bound that finished.
Scores use the contest formula ⌊1000 · Σ saved latency × count ÷ Σ count⌋ after merging duplicate (video, endpoint) lines. An endpoint linked twice to the same cache counts with its better latency.
